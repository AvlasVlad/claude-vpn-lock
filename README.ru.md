# claude-vpn-lock

**Claude ходит к Anthropic только через ваш VPN.** Если VPN пропал на долю секунды,
переподключился или сама VPN-программа решила пустить Claude «напрямую», ядро macOS отбивает
пакеты. Окна нет: решение принимается на каждом пакете, а не скриптом, который сначала должен
что-то заметить.

Работает сразу для всего: приложение Claude, Claude Code в терминале, расширение VS Code.
Пока только macOS. [English version](README.md).

> Неофициальный инструмент сообщества. Не связан с Anthropic и не одобрен ею.

## Зачем

VPN-программа «протекает» тремя обычными способами, и каждый раз Claude говорит с Anthropic
с вашего настоящего адреса:

1. **Туннель пропал** на мгновение (смена Wi-Fi, сон, сбой сервера).
2. **VPN переподключился** и создал новый туннель (`utun36` стал `utun38`).
3. **Раздельная маршрутизация**: правила самой VPN-программы пускают часть трафика
   «напрямую», мимо туннеля, а значок VPN при этом показывает «подключено».

Аварийный выключатель (kill switch) большинства VPN-программ третий случай не закрывает, а
системный выключатель macOS не трогает трафик, который сама VPN-программа отправляет напрямую.

## Как устроено

```
Claude (любой) --> пакет к Anthropic --> ядро macOS, правило pf:
                                         «к сетям Anthropic — только через utun38»
                                          |
          уходит через utun38 (VPN)  <----+  пропустить
          уходит через en0 (Wi-Fi)   <----+  отбить сразу («соединение отвергнуто»)

Демон (не на пути пакета):
  туннель появился/сменился --> проверить страну выхода через него --> не запрещена? --> «только через utunN»
  туннеля нет / страна запрещена --> «к Anthropic — никак»
  каждые 30 с --> перепроверить страну выхода
  каждые 5 с  --> pf включён? правило на месте? (если нет — вернуть)
```

**pf** — встроенный в macOS пакетный фильтр. Правило лежит в гнезде
`com.apple/000.ClaudeVPNLock`, которое штатный `/etc/pf.conf` уже подключает строкой
`anchor "com.apple/*"`, поэтому `/etc/pf.conf` не правится.

## Что нужно

- macOS со штатным `/etc/pf.conf` (проверено на macOS 26 Tahoe, Apple silicon).
- VPN-программа в **режиме TUN** (создаёт интерфейс `utunN`, macOS помечает его как VPN).
  Проверено с **Happ**. Должно работать с WireGuard, Outline, V2Box, Hiddify, Clash Verge,
  sing-box в режиме TUN, но пока не проверено — напишите, если попробуете.
- Учётная запись администратора.

## Установка

Сначала **включите VPN**: без него установщик не запустится.

```bash
git clone https://github.com/AvlasVlad/claude-vpn-lock.git
cd claude-vpn-lock
bash install.sh --dry-run     # план и проверка VPN; ничего не меняет
sudo bash install.sh          # установка и доказательство, что защита работает
```

Перед завершением установщик доказывает работу защиты. Контрольный пакет мимо туннеля
обязан быть отбит ядром (иначе всё откатывается само), затем один запрос к Anthropic через
туннель. Проверять «проходит ли» запросами к Anthropic мимо туннеля он не будет никогда:
отбитие доказывается на `203.0.113.7` — адресе, зарезервированном для документации и не
существующем в интернете.

### Или пусть поставит Claude Code

Вставьте в Claude Code:

```text
Установи claude-vpn-lock на этот Mac: https://github.com/AvlasVlad/claude-vpn-lock
Склонируй, прочитай README.ru.md и все скрипты до запуска и объясни простыми словами, что
изменится. Запусти `bash install.sh --dry-run` и покажи результат.
Установке нужен мой пароль администратора: дай мне точную команду `sudo bash install.sh`,
чтобы я запустил её сам в своём терминале, дождись меня, прочитай вывод и объясни его.
Никогда не проверяй, «проходит ли» Claude, запросами к Anthropic мимо VPN.
```

## Проверить, что работает

```bash
sudo bash check.sh            # полная проверка, доказательства — счётчики pf (безопасна: защиту не снимает)
sudo bash check.sh --short    # только главные проверки
sudo bash vpn-off-test.sh     # вы выключаете и включаете VPN, скрипт следит каждую секунду
```

Или просто: выключите VPN — Claude перестанет отвечать. Включите — заработает примерно через
секунду.

## Удалить

```bash
sudo bash uninstall.sh --dry-run   # что будет удалено
sudo bash uninstall.sh             # удалить всё и сверить машину со снимком до установки
```

## Что закрыто и что нет

| Случай | Что будет |
|---|---|
| VPN пропал на долю секунды | пакеты к Anthropic отбиты ядром, окна нет |
| VPN пересоздал туннель под новым именем (`utun36` -> `utun38`) | новый туннель закрыт, пока не проверена страна выхода |
| VPN пересоздал туннель под тем же именем | трафик всё равно идёт через VPN; страна выхода перепроверяется, как только демон заметит (событие маршрута, не дольше одного тика в 5 с) |
| VPN-программа шлёт Anthropic напрямую, мимо туннеля | отбито ядром, окна нет |
| Сервер VPN в запрещённой стране (`BLOCKED_COUNTRIES`) | закрыто после проверки: сразу при подключении, **до 30 с** при смене сервера без переподключения. Пока проверка страны не отвечает (Cloudflare и запасные адреса молчат), действует последний вердикт |
| Страну выхода нового туннеля проверить не удалось | открыто, с пометкой в журнале (`COUNTRY_FAIL=open`, можно `closed`) |
| Кто-то выключил pf, стёр правило или таблицу | вернётся на следующем тике в 5 с (замерено 5–6 с; до ~13 с, если в этот момент идёт проверка страны), запись в журнал; уведомление на экране — если выключили pf |
| Что-то заменило весь набор правил pf без штатной строки `com.apple/*` (аварийный выключатель другого VPN, свой `pf.conf`) | **защита не может работать.** Замечается за 60 с: запись в журнал и уведомление |
| Демон упал | последнее правило остаётся; launchd перезапустит демон за 5 с |
| Загрузка Mac | демон стартует с «закрыто», пока туннель не проверен |
| Сети с IPv6 | Anthropic по IPv6 (`2607:6bc0::/32`) отбит тем же правилом |
| Поездка без VPN | **Claude не работает.** В этом и смысл: только через VPN |
| `a-cdn.claude.ai`, `status.claude.com` без VPN | **не закрыто**: они на Amazon CloudFront вместе с тысячами чужих сайтов, закрыть их адреса — сломать чужое. Это статические файлы и страница статуса, не запросы к модели |
| Отчёты об ошибках других программ в Sentry / Datadog | Claude шлёт отчёты в общие адреса Sentry и Datadog, поэтому и они разрешены только через VPN. Другие программы, отчитывающиеся туда же, затронуты так же |

## Настройки

`/opt/claude-vpn-lock/claude-vpn-lock.conf` (после правки:
`sudo launchctl kickstart -k system/io.github.avlasvlad.claude-vpn-lock`):

- `BLOCKED_COUNTRIES="RU BY"` — страны выхода, в которых Claude запрещён (двухбуквенные
  коды; проверяется через туннель по Cloudflare `/cdn-cgi/trace`).
- `COUNTRY_INTERVAL=30` — как часто перепроверять страну выхода, секунд.
- `COUNTRY_FAIL=open` — новый туннель, страну которого проверить не удалось: `open`
  (с пометкой в журнале) или `closed`.
- `DIRECT_POLICY=block` (по умолчанию) или `country` — см. следующий раздел.
- `DIRECT_INTERVAL=10` — при `country`: как часто заново спрашивать страну выхода прямой
  сети, секунд (открытой или заблокированной).

### По желанию: без VPN там, где Claude разрешён

По умолчанию замок требует VPN всегда. Если вы живёте или путешествуете в стране, которой
**нет** в `BLOCKED_COUNTRIES`, поставьте `DIRECT_POLICY=country`:

- **VPN выключен, обычная сеть (Wi-Fi, Ethernet, раздача с телефона: `en0`, `en1`...)** —
  демон спрашивает через саму эту сеть, в какой стране её собственный выход. Страна
  разрешена — Claude работает напрямую, без задержки VPN. Правило привязывается к этому
  интерфейсу (`block ... on ! en0 ...`), поэтому включённый позже VPN заблокирован, пока
  не проверена страна его выхода.
- **Запрещённая страна или ответа получить не удалось — закрыто.** Неизвестная страна
  в прямой сети никогда не разрешается, даже если сеть только что была открыта
  (`COUNTRY_FAIL` на неё не действует).
- **VPN включён** — всё как раньше. Туннель с выходом из `BLOCKED_COUNTRIES` (например,
  российский VPN, который вы включили для проверок) оставляет Claude заблокированным.
- **Сеть сменилась** (другой Wi-Fi, другой шлюз, даже в том же диапазоне адресов) — замок
  закрывается и проверяет заново, прежде чем открыться. По событию маршрутизации это сразу;
  если событий нет — за один такт в 5 с.

У этого режима есть окно реакции, которого нет в режиме туннеля: имя интерфейса при смене
сети остаётся `en0`, поэтому в первые моменты после смены прежнее правило ещё действует.
Если адрес, шлюз и его MAC остаются прежними, а страна выхода меняется (раздача с телефона
после смены SIM, дорожный роутер), никакое событие этого не объявляет, и окно — до
`DIRECT_INTERVAL` секунд (по умолчанию 10). Если это неприемлемо — оставьте `block`. Пока
разрешена прямая сеть, `check.sh` выполняет другие проверки (D2–D4).

## Журнал и состояние

```bash
sudo /opt/claude-vpn-lock/claude-vpn-lock-daemon.sh status
tail -f /var/log/claude-vpn-lock.log
```

- `STATE open :: ... exit NL 192.0.2.52` — туннель проверен, Claude работает.
- `STATE closed :: no VPN tunnel ...` — VPN нет, Claude отбит.
- `PF rule being replaced had blocked N packets` — сколько пакетов отбито, пока стояло это правило.

## Куда ходит в сеть

- Демон, через туннель: `https://1.1.1.1/cdn-cgi/trace` раз в 30 с, чтобы узнать страну
  выхода (запасные: `www.cloudflare.com/cdn-cgi/trace`, `ipinfo.io/json`); раз в 30 минут —
  DNS-запросы имён Anthropic через системный резолвер.
- `install.sh` и `check.sh`: один запрос к `https://api.anthropic.com/` через туннель (IPv4),
  никогда мимо него. Контрольный пакет на `203.0.113.7`, который отбивается, не выйдя наружу.
- Только `check.sh`: `77.88.44.55` (адрес, который многие VPN пускают «напрямую», — показать,
  что такой трафик тоже режется; заменить: `CVL_DIRECT_TEST_IP=...`), а также
  `api.github.com`, `registry.npmjs.org`, `pypi.org`, `www.cloudflare.com` (показать, что
  остальные сервисы работают).

## Безопасность

- Всё, что выполняется от root, лежит в `/opt/claude-vpn-lock` и принадлежит root. Не в
  `/usr/local`: на Intel-Mac с Homebrew эта папка принадлежит пользователю, и он мог бы
  подменить то, что исполняет root. Установщик откажется ставить, если `/opt` может менять не
  root, а демон проигнорирует свой конфиг (и запишет это в журнал), если файл или папка над
  ним доступны на запись не только root.
- В macOS pf по умолчанию выключен. Если он выключен, а другие правила уже загружены, его
  включение заставило бы работать и их; установщик покажет их и остановится
  (`--enable-pf-anyway` — ставить всё равно).

## Ограничения

- Диапазоны Anthropic `160.79.104.0/21` и `2607:6bc0::/32` зашиты в демон. Адреса вне их
  (загрузки, ассеты, телеметрия) демон узнаёт из DNS раз в 30 минут и помнит 30 дней. Если
  Anthropic переедет на новые адреса, защита неполна, пока DNS их не подскажет.
- VPN в **режиме прокси** (без интерфейса TUN): установщик ставить не станет. Если переключить
  VPN-программу в режим прокси после установки, защита останется «закрытой»: программы,
  которые ходят через прокси, работают, а те, что его игнорируют, отбиты (так задумано; не
  проверялось).
- `DIRECT_POLICY=country`: страна берётся по адресу выхода так, как его видит Cloudflare
  (только IPv4); ошибка или устаревшая запись в гео-базе — неверный вердикт. Прямой сетью
  считаются только интерфейсы `en*`; мосты и сотовые связи остаются закрытыми. Окно реакции
  после смены сети описано в «Настройках».
- Пока защита стоит, pf включён (в macOS он по умолчанию выключен).
- `check.sh --heal-tests` (его использует `tests/acceptance.sh`) на несколько секунд снимает
  правило, чтобы доказать, что демон его вернёт. В эти секунды Anthropic мимо туннеля не
  отбивается, поэтому по умолчанию эти проверки выключены.
- После удаления `pfctl -s Anchors` может ещё показывать пустые узлы
  `com.apple/00x.ClaudeVPNLock*` (0 правил, 0 таблиц). Ядро macOS убирает пустые узлы только
  при перезагрузке; ни на что не влияют.

## Как проверялось

На настоящем Mac (macOS 26, Apple silicon, VPN Happ) полная приёмка `tests/acceptance.sh
--with-vpn-off` этой версии прошла все шаги: сухие прогоны ничего не меняют, установка,
полная проверка, выключение и включение VPN руками, удаление, повторная установка. Из этого
прогона (4 октября 2026):

- VPN выключен 11 с: **0** соединений Claude к Anthropic с настоящего адреса; ядро отбило 51
  пакет к Anthropic; контрольный пакет отбит 10 раз из 10. Первые 2 с демон ещё даже не
  заметил пропажи (показывал «открыто»), а пакеты уже отбивались: блокирует правило, а не
  демон. Через 1 с после включения VPN Claude снова открыт.
- Пакет к `160.79.104.10` с Wi-Fi: отвергнут сразу, счётчик правила +1. Через туннель
  Anthropic отвечает, счётчик не меняется. 51 живое соединение Claude — все с адреса туннеля.
- Собственный прямой трафик VPN-программы (к тестовому адресу, который она пускает
  «напрямую») режется таким же правилом: HTTP 406 -> отвергнуто -> 406.
- GitHub, npm, PyPI, Cloudflare при включённой защите отвечают как обычно.
- Правило, снятое руками, вернулось за 6 с; очищенная таблица — за 1 с; после
  `pfctl -f /etc/pf.conf` правило на месте, чужие гнёзда не изменились.
- Удаление: машина совпадает со снимком до установки построчно.

`DIRECT_POLICY=country` (1.1.0) принят на том же Mac 28 октября 2026 скриптом
`tests/acceptance-direct.sh` в сети, собственный выход которой разрешён:

- VPN выключен: демон проверил страну выхода сети и открыл правило на `en0`; `check.sh`
  (D2–D4) прошёл; Anthropic ответил напрямую, счётчик правила не сдвинулся.
- Страна самой сети на несколько секунд добавлена в `BLOCKED_COUNTRIES`: замок закрылся, ядро
  отвергло и контрольный пакет, и пакет к `160.79.104.10` (счётчик правила +3). Конфиг вернулся,
  замок снова открылся.
- VPN снова включён: демон проверил выход туннеля и перепривязал правило к нему, контрольный
  пакет с адреса Wi-Fi отвергнут (curl, код 7). Последнее утверждение скрипта поправлено
  после прогона (он замерил за момент до переключения демона); результат подтверждён журналом
  демона и вручную.

Логику демона покрывает и `tests/sim.sh`: 119 проверок на поддельных `pfctl`, `route`,
`ifconfig`, `arp`, `curl` и поддельных часах, без root. Запускается на каждое изменение. Для
каждого решения прямого режима показано, что тест краснеет, если решение убрать.

## Windows, Linux

Пока нет. Идея переносится: правило брандмауэра, которое пускает адреса Anthropic только через
интерфейс VPN, плюс небольшая служба, которая держит правило на правильном интерфейсе.
Для Windows с Clash/Mihomo в режиме TUN есть отдельный проект:
[wlsnD7/claude-kill-switch-windows](https://github.com/wlsnD7/claude-kill-switch-windows).
Пулл-реквесты приветствуются.
